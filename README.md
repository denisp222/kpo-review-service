# Проверка учебных работ

Учебный модуль проекта по КПО. Преподаватель выставляет оценку от 0 до 100, добавляет комментарий и рекомендации либо отклоняет работу с указанием причины. Студент читает результат и свои уведомления.

Это серверная часть модуля, а не всё приложение. React-интерфейс, курсы, загрузка файлов и полноценная авторизация относятся к следующим этапам. Демонстрационные токены заменяют вход двух тестовых пользователей.

## Структура

```text
src/http/                 HTTP API и демонстрационная авторизация
src/reviews/              правила проверки, IReviewRepo и INotificationRepo
src/infrastructure/       реализация хранилищ через Prisma
prisma/                   схема, миграции и тестовая работа
tests/unit/               правила проверки и авторизация
tests/integration/        HTTP API с настоящей PostgreSQL
scripts/                  проверки и сбор метрик
.github/workflows/        CI и выпуск версии
docs/metrics/             снимки результатов по этапам
```

Используются TypeScript, Express, Prisma и PostgreSQL 16 — серверные технологии из лабораторной №4. Реализация хранилища передаётся сервису через интерфейс. Решение и уведомление записываются одной транзакцией. Повторная и одновременная проверка не перезаписывают уже сохранённый результат.

## Запуск

Нужны Node.js 24 LTS, Git и PostgreSQL 16. Для запуска баз через `compose.yaml` нужен работающий Docker Desktop. Существующий PostgreSQL также подходит: создайте отдельные базы и измените адреса подключения.

```powershell
npm ci
Copy-Item .env.example .env
docker compose up -d db
npm run db:generate
npm run db:migrate
npm run db:seed
```

В `.env` задайте два разных случайных значения `DEMO_TEACHER_TOKEN` и `DEMO_STUDENT_TOKEN`. Для каждого значения выполните:

```powershell
node -e "console.log(require('crypto').randomBytes(24).toString('hex'))"
```

```powershell
npm run dev
```

API доступен по адресу `http://127.0.0.1:3000`. Проверка запуска: `GET /health`. Начальная работа — `work-1`. В заголовке передавайте `Authorization: Bearer <токен>`.

| Запрос                          | Назначение                                     |
| ------------------------------- | ---------------------------------------------- |
| `GET /api/works/work-1`         | Прочитать работу своего студента / свою работу |
| `POST /api/works/work-1/review` | Проверить работу от имени преподавателя        |
| `POST /api/works/work-1/reject` | Отклонить работу от имени преподавателя        |
| `GET /api/notifications`        | Прочитать уведомления студента                 |

Тело запроса для проверки:

```json
{ "grade": 85, "comment": "Решение верное", "recommendations": "Добавить тесты" }
```

Для отклонения: `{"reason":"Нет решения задания"}`. Для повторной демонстрации используйте новую работу в базе. Итоговое решение по одной работе повторно не изменяется.

## Проверки

Интеграционные тесты очищают специально выделенную тестовую базу. Её имя должно заканчиваться на `_test`. Не указывайте в `TEST_DATABASE_URL` рабочую базу.

```powershell
docker compose --profile test up -d test-db
$env:DATABASE_URL = 'postgresql://review:local_test_password@127.0.0.1:5439/review_test'
npm run db:migrate
Remove-Item Env:DATABASE_URL
npm run quality
```

`TEST_DATABASE_URL` читается из `.env`. В CI обе переменные указывают на отдельный PostgreSQL service container.

`quality` последовательно запускает Prettier, ESLint, проверку типов и Vitest с покрытием. При успехе выполняется сборка в `dist`. Порог покрытия строк, ветвей, функций и операторов — 80%. Исключён только `src/server.ts`, который запускает сервер; HTTP-обработчики, правила и хранилище входят в расчёт.

Отчёты: `reports/metrics.json`, `reports/metrics.md`, `reports/junit.xml`, `reports/coverage/index.html`. Неудачные проверки возвращают ненулевой код завершения. Интеграционные тесты проверяют PostgreSQL, права доступа, параллельные запросы и откат транзакции при ошибке уведомления.

## Работа с Git

Выбран GitHub Flow: `main` содержит проверенную версию; изменения выполняются в коротких ветках `feature/<задача>` или `fix/<ошибка>`. Для небольшого учебного проекта отдельная постоянная ветка `develop` не требуется.

```powershell
git switch main
git pull --ff-only
git switch -c feature/my-change
# Изменение файлов и npm run quality
git add .
git commit -m "feat: add my change"
git push -u origin feature/my-change
```

Сообщение коммита: `тип: краткое описание`; типы `feat`, `fix`, `test`, `docs`, `ci`, `chore`, `refactor`. Например, `fix: reject repeated review`. Заголовок pull request оформляется так же.

После `npm ci` Husky включает локальные проверки: `pre-commit` проверяет формат, линтер и типы; `commit-msg` проверяет Conventional Commits. В CI повторно проверяются все новые коммиты и заголовок PR, поэтому пропуск локального hook не отменяет проверку на сервере.

Слияние выполняется через pull request методом **Create a merge commit**. Обязательная проверка — `quality`; ветка должна быть обновлена относительно `main`. Правила защиты нужно установить в настройках GitHub: одного файла workflow для защиты ветки недостаточно. Проверка рецензентом желательна, но обязательное чужое одобрение для индивидуального проекта не задаётся.

## Метрики и этапы

После каждого push и PR Actions сохраняет метрики в артефакте `quality-reports-<run_id>`. При успехе дополнительно сохраняется `build-<commit>`. Срок хранения артефактов — 90 дней.

Собираются ошибки и предупреждения ESLint, число успешных, неуспешных и пропущенных тестов, время тестов, покрытие строк и ветвей, время сборки и всего набора проверок. `testSeconds` включает запуск Vitest и расчёт покрытия. `qualitySeconds` не включает установку зависимостей и подготовку БД.

Для фиксации завершения этапа:

```powershell
npm run snapshot -- --stage infrastructure
git add docs/metrics
git commit -m "docs: record infrastructure metrics"
```

Этапы из плана: `prototype`, `infrastructure`, `implementation-1`, `implementation-2`, `implementation-3`, `testing`, `release`. Первый замер этого модуля обозначается `lab5-baseline`; он не подменяет отсутствующие замеры прошлых этапов. Файл содержит время и SHA проверяемого коммита. Сначала сохраните код коммитом, затем выполняйте снимок.

Альтернатива: **Actions → CI → Run workflow**, выбрать этап. JSON снимка попадёт в артефакт. Скачайте и сохраните его в репозитории через PR, чтобы результат оставался доступным после истечения срока хранения артефактов.

## Выпуск версии

После успешного PR обновите `package.json`, `package-lock.json` и `CHANGELOG.md`. На проверенном коммите `main` создайте аннотированный тег:

```powershell
git switch main
git pull --ff-only
git tag -a v0.1.1 -m "Release 0.1.1"
git push origin v0.1.1
```

CI заново проверяет тег. Release создаётся только после успешных проверок, совпадения тега с версией пакета и проверки, что коммит входит в историю `main`. Архив содержит `dist`, схему и миграции Prisma, `package.json` и lock-файл. Для запуска после распаковки выполните `npm ci`, `npm run db:generate`, настройте `.env`, примените миграции и выполните `npm start`.

Автоматическое развёртывание не включено: это необязательный пункт лабораторной. `compose.yaml` поднимает только локальные базы для разработки и тестов. Полная схема развёртывания из лабораторной №4 с Nginx, React и файловым хранилищем здесь не реализована.
